## 1. Research question

Whether implicit gender biases are present in multi-agent LLM interactions, and whether they
can be mitigated (Abstract; §1).

The framing given for why this matters: LLMs are increasingly used to simulate societies and
carry out social tasks, so biases absorbed from human-generated training data propagate into
those simulations; and implicit biases are specifically harder to catch than explicit ones
because they stay hidden and can shape outputs without the user or the model registering them
(Abstract; §1).

The paper states three contributions: a dataset of scenarios in which implicit gender bias may
arise, a metric for measuring it in task assignments, and two mitigation strategies (§1).

## 2. Setup

**Models.** Three: `gpt-35-turbo`, `gpt-4`, and the open-source `mistral-7b-instruct` (§5).
Fine-tuning experiments used `gpt-35-turbo-0613` and `mistral-7b-instruct`; the authors note
in a footnote that gpt-4 could not be fine-tuned at the time (§6.1, footnote 7), which is why
gpt-4 appears only in the self-reflection mitigation results.

**Demographic attribute varied: gender only** — male and female. Race and religion are named
explicitly as *future* work, not as part of this study (§7; §8).

**How personas were specified.** This is the design feature most worth noting. Personas
consist of **a name and a gender label, and deliberately nothing else** — no skills, no
backstory, no stated competence. The authors say the restriction is intentional, so that the only
difference between personas is gender (§5). The worked example in Figure 2 lists the
characters of a school-domain scenario as Rachel (female), Alex (male), James (male) and Lily
(female).

The authors return to this point when interpreting their results: gendered justifications
appeared in the transcripts even though the persona descriptions contained no skill
information or reasons, only name and gender (§7).

**Scenario dataset.** Seven domains chosen as areas susceptible to implicit bias: family,
office, hospital, politics, law enforcement, education and team dynamics (§3). Scenarios were
generated by gpt-4 in the form of a scenario description and goal, associated tasks, and
characters involved. The main **Scenarios Dataset contains 111 scenarios**, each with three or
four tasks and three or four characters (§3).

Each scenario is constructed so that it contains both stereotypically male and stereotypically
female tasks, with the number of tasks of each type equal to the number of characters of each
gender, giving an equal number of characters and tasks (§3). The grounding for which tasks
count as stereotypically male or female is drawn from prior literature on human role
allocation, which the paper cites for the claim that males tend to be assigned hands-on,
technical and leadership roles while females are assigned organisational or non-technical ones
(§3).

Two further datasets (§3):
- a **Fine-tune Dataset** built from the same scenarios, with assignments manually created in
  two settings — with implicit bias (stereotypical tasks to the matching gender) and without
  (each stereotypical task type assigned to both genders) — and gpt-4-generated reasons for
  the presence or absence of bias;
- a **Test Dataset** of **32 scenarios** in two *additional* domains, media and movies, and
  planning and development, with two to four tasks and characters, used to check whether
  mitigation generalises beyond the fine-tuning domains.

**Human validation of the generated data.** Because gpt-4 generated the scenarios, the
Fine-tune Dataset was checked by human annotators: the dataset was split into four sections
with two annotators per section, eight annotators in total, judging whether implicit bias was
present in the assignments and why. Average Cohen's kappa was **0.823**, and agreement between
the human and gpt-4 annotations was **86.28%** (§3).

**Number of runs.** Scores are averaged over **five LLM runs** (§4; §5.1.1).

## 3. Interaction design

**Multi-agent.** Each scenario is run with three or four agents, one per character. Each agent
is instantiated as a **separate LLM instance**, so parameters and information are not shared
between them, and each keeps its own memory of generated outputs (§5).

**Task type: contested task assignment.** Agents allocate a fixed set of tasks among
themselves.

**Is anything actually contested?** **Yes — but only in one of the three settings**, and the
distinction is central to reading this paper's results. The three settings are (§5.1.1):

1. **no interaction** — a single agent produces an assignment with no dialogue at all;
2. **interaction, no goal** — agents converse and have full control over the assignment, with
   no private incentive;
3. **interaction, goal** — each agent is *privately* instructed to assign one particular
   common task to itself before the first assignment round. Because every agent receives the
   same private instruction, every agent claims the same task, and the group must resolve who
   gets it.

Setting 3 is the genuinely contested one. The authors' stated expectation was that this
controlled setup would *lower* the initial bias score, since everyone claims the same task
(§5.1.1).

**Turn structure** (§5, Fig. 1):

1. **First assignment** — agents take turns assigning tasks to all agents. Each agent knows
   only the other agents' personas and **cannot see other agents' responses until it has made
   its own assignment**.
2. **Two discussion rounds.**
3. **Final assignment** — each agent gives its final allocation based on the whole discussion.

Agent order follows the character sequence in the dataset, but the authors ensure scenarios
have random gender orders, and state that they randomise agent order to eliminate position
bias (§5; §1). Agents are not required to produce identical assignments (§5, footnote 5).

**Termination condition:** the fixed protocol above — first assignment, two discussion rounds,
final assignment. There is no agreement-based stopping rule.

## 4. How the effect was measured

**The metric is a bias score over task assignments** (§4).

Each assignment is classified as one of three types (§4):
- **stereotypical** — tasks allocated in line with gender stereotypes;
- **anti-stereotypical** — the reverse allocation;
- **neutral** — tasks evenly distributed across genders.

For scenarios with an odd number of characters or tasks, the paper defines a *balanced
stereotypical pair*: if two stereotypically male or female tasks are split between one male
and one female, that pair is balanced. With F female and M male agents, the maximum possible
number of balanced stereotypical pairs is min(F, M). An assignment is neutral when the number
of balanced stereotypical pairs equals min(F, M); if it is lower, the assignment is
stereotypical when the remaining stereotypical assignments outnumber the anti-stereotypical
ones, and anti-stereotypical otherwise (§4).

Writing a for the total number of assignments, and b_n, b_a, b_s for the counts of neutral,
anti-stereotypical and stereotypical assignments respectively (so that b_n + b_a + b_s = a),
the score averaged over five runs is (§4, Equation 1):

> Average Bias Score = (1/5) · Σ over runs i of [ (−1)·(b_a,i / a) + 0·(b_n,i / a) + 1·(b_s,i / a) ]

So a **positive score means stereotypical, pro-male assignment; a negative score means
anti-stereotypical; zero means balanced**.

The paper adds a footnote distinguishing two different routes to a zero score: equal numbers
of stereotypical and anti-stereotypical assignments, versus all assignments being neutral. It
notes these are systematically different situations and that the first case was not observed
in its experiments (§5.1.1, footnote 4).

**Conditions compared:** the three settings above, and within the interacting settings,
**first-response versus last-response**, which is how the effect of dialogue is isolated
(§5.1.1, Table 1). Results are also broken down by the seven domains (§5.1.2).

### 5b. The central finding: interaction amplifies

Bias scores rise from first response to last response in **every model and every setting**
(§5.1.1; Table 1 caption). The authors add that despite lower first-response scores in the
goal setting, biases escalate to equal or higher levels there than in the no-goal setting
(§5.1.1).

In other words, the setting deliberately designed to *suppress* initial bias ended up with
among the highest final scores: gpt-35-turbo goes 0.2727 → 0.5741, and mistral 0.2527 →
0.5722.

### 5c. Domain breakdown

Bias scores increase after interaction **across all seven domains** (§5.1.2). Every model
produced a positive bias score in every domain. The domain with the lowest bias score across
all settings was Legal; Legal and Office were low across models in the no-interaction setting
(§5.1.2).

### 5d. Model size

Larger models were more biased, not less: gpt-4 exhibits the highest bias scores, which the
authors read as suggesting that larger models, while potentially more helpful, may also
exhibit higher levels of bias (§7).

### 5e. What the transcripts looked like

The justifications agents gave for their assignments predominantly aligned with traditional
gender norms, despite the personas containing only a name and a gender (§7).

## 6. What "bias" is measured against

**Standard (a): deviation from equal treatment across groups — a fairness standard.**

The reasoning, from the metric definition in §4:

- The zero point of the bias score is an **even distribution of tasks across genders**. Neutral
  is defined as balanced, not as "matching what real mixed-gender groups do".
- The paper positions its metric alongside fairness metrics such as demographic parity and
  equalized odds, which it describes as aiming to ensure equality across groups or individuals,
  and explains that it needed a task-assignment-specific metric because those existing metrics
  did not suit its framework (§4).
- The mitigation target is explicitly a score near zero: the best result is reported as a bias
  score of 0.01, described as almost neutral or no bias (§6.3).

**Where human data does enter, and where it does not.** Human evidence is used **to define
which tasks count as stereotypically male or female** — that coding is grounded in prior
literature on human role allocation (§3). Human annotators were used to validate that the
generated scenarios do contain implicit bias, with Cohen's kappa 0.823 and 86.28% agreement
with gpt-4 (§3).

But **no human behavioural baseline is collected or compared**. The paper does not measure how
real mixed-gender groups allocate these tasks and does not compare the LLM's bias score to any
human bias score. The psychological theories invoked in §7 — Stereotype Threat Theory and
Groupthink — are offered as *explanations* for why bias might amplify in groups, not as
measured human comparisons.

**So: standard (a) only.** This paper cannot tell the FYP whether the LLM's gendered
assignment pattern resembles or exaggerates what humans do.

## 7. Mitigation

**Two approaches, plus an ensemble** (§6):

1. **Supervised fine-tuning (FT)**, which changes model parameters. Two data settings: the
   **full** Fine-tune Dataset (both biased and unbiased scenarios) and **half** of it (only
   non-biased scenarios). The stated hypothesis is that a full-data model can distinguish
   biased from unbiased scenarios, while a half-data model may not make that distinction but
   could be better at generating unbiased assignments because it sees only equal
   representation. An 80/20 train/dev split was used, on `gpt-35-turbo-0613` and
   `mistral-7b-instruct` (§6.1).
2. **Self-reflection (SR)**, which changes no parameters, in two variants: without in-context
   examples (no-ICE) and with them (ICE) (§6.2).
3. **Ensemble** of fine-tuning and self-reflection (§6).

**Reported effects:**

- The best single result is **`ft-gpt-35-turbo` with SR + ICE, giving a bias score of 0.01**,
  which the authors describe as almost neutral (§6.3).
- All ensembles of fine-tuning plus self-reflection performed best for both gpt-35-turbo and
  mistral-7b-instruct (§6.3).
- Of the two approaches individually, fine-tuning was more effective than self-reflection,
  visible from the first responses onward (§6.3).
- Fine-tune and test data came from **different domains**, which the authors offer as evidence
  that fine-tuning generalises (§6.3).
- Changes in bias score after interaction were minimal for fine-tuned agents, because their
  first responses were already less biased (§6.3).
- **gpt-4 over-corrected.** With mitigation, gpt-4 produced *negative* bias scores, i.e.
  anti-stereotypical assignments, and did not produce equally representative assignments after
  self-reflection (§6.3; §8).
- Smaller models benefited more from the mitigation strategies than larger ones (§6.3; §7).

**`[inference]` — would this mitigation move the LLM toward or away from realistic human group
differences?**

**Away from realism, or at least orthogonally to it — and the paper gives no way to tell
which.** The mitigation optimises toward a bias score of zero, which is defined as parity.
Nothing in the design measures whether parity is what real mixed-gender groups produce. If
real groups allocate tasks with some gender skew, then a model tuned to zero has been tuned
*past* human behaviour rather than toward it. The gpt-4 over-correction into negative scores
is a concrete instance of the risk: the model was pushed beyond parity into a counter-stereotypical
pattern that is no more human-realistic than the original. This is the fairness-versus-realism
tension the FYP has to navigate, and it is developed further in
[`reading-notes-demographics.md`](reading-notes-demographics.md).

## 8. Limitations stated by the authors

From §8, Limitations:

- **gpt-4 produces negative biases after mitigation**, which the authors say requires further
  analysis, and current mitigation approaches for gpt-4 — specifically self-reflection — have
  not been found to address the issue effectively.
- **gpt-4 could not be fine-tuned**, so its evaluation is limited to self-reflection only, a
  constraint the authors emphasise.
- They state they plan to analyse why gpt-4 has the highest biases.
- **Most of the data was generated by gpt-4**, and the authors advise approaching results
  produced by gpt-4 with a degree of scepticism.
- **The dataset is limited to 111 scenarios**, which they attribute partly to the scarcity of
  implicit bias scenarios in the literature.
- The scope is gender only; extending to religion, race and other factors is future work.

From §9, Ethical Considerations: the authors note that data generated by gpt-4, although
validated by humans, may contain hidden biases of the kind found in models pretrained on
human-generated data.

## 9. Relevance to this FYP

`[inference]` — my judgement.

1. **The amplification result is the one that matters most.** Bias rose from first to last
   response in all six interacting conditions. GameChat-style conflict resolution is exactly
   this architecture: separate LLM instances, multiple turns, each seeing the other's messages.
   If the FYP measures a demographic effect from a single-shot prompt — which is what
   `run01` does — that measurement may understate what appears once agents actually negotiate.
   This is a testable prediction, not an established fact about the FYP's setting.
2. **The "goal" condition is a ready-made experimental design.** Give both agents the same
   private instruction to claim priority, then measure who concedes, broken down by persona
   gender. It is the closest thing in these five papers to a contested-priority protocol, and
   it is cheap to adapt.
3. **The persona design is the cleanest template available.** Name plus gender and nothing
   else, with randomised gender order and a separate LLM instance per agent. If the FYP wants
   to isolate a gender effect rather than confound it with implied competence, this is how.
4. **But it cannot answer the FYP's actual question.** It measures deviation from parity, not
   deviation from human behaviour. For the realism-versus-artifact judgement the parent issue
   is built around, this paper supplies the LLM side and nothing else.
5. **A caution that applies directly to `run01`.** The authors advise treating gpt-4-generated
   data with scepticism because the same model produced the data and the results. `run01`
   generates with DeepSeek and validates with automated checks over the same outputs; the
   structural concern is the same one.
